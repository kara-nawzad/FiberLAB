- **HTML entry:** `index.html` → `<div id="root">` + `<script type="module" src="/src/main.tsx">`.
- **JS entry:** `src/main.tsx` imports the four CSS layers in order (`@xyflow` → `tokens.css` → `global.css` → `theme.css` → `photo-ui.css`), registers `window` `error`/`unhandledrejection` loggers (`main.tsx:18-23`), then renders `<ErrorBoundary><App/></ErrorBoundary>` in StrictMode.
- **App shell:** `src/App.tsx` exports `default App` (view switch landing↔studio, `App()` at L1453) and `StudioWorkspace` (L215+), both wrapped by one `ReactFlowProvider` (L1494).
- **Module layout:**
  - `src/engine/` — pure domain logic: optical simulator, OTDR simulator, OPM probe, presets, missions, node factories, edge decoration, landing physics.
  - `src/data/` — static data: hardware catalogue (with inline SVG art), pricing catalogue, quotation export helpers.
  - `src/components/` — UI; `nodes/` are React Flow node renderers, `landing/` is the marketing/overview page, `hardware/` renders catalogue art.
  - `src/hooks/`, `src/context/` — a11y dialog hook, section focus/history, simulation context.
  - `src/styles/` — tokens → global → theme → photo-ui (last wins).
- **Lazy loading:** `BOMModal`, `OtdrModal`, `MissionDrawer` are `React.lazy` chunks (`App.tsx:111-115`) each with an `OverlayLoading` fallback (`App.tsx:117-127`).
- **Vendor chunking:** `vite.config.ts` `manualChunks` splits `flow` (xyflow + d3), `react`, `icons`, and everything else.

There is **no "project" object**. A design is the tuple `(nodes, edges, settings, unitCosts)`. Node ids are generated (`engine/factories.ts:37` → `` `${kind}-${Date.now().toString(36)}-${seq}` ``), so they are opaque strings.

```
TopologyExport {
  format: 'ftth-studio/topology'
  version: 2
  exportedAt: ISO string
  settings: { safetyMarginDb: number, autoRun: boolean }
  nodes: PonNode[]            // full React Flow nodes incl. data + position
```

## 1.5 What the tool does, in plain words, as implemented

FiberLAB is a single-page browser app with two full-screen views:

1. **Landing / overview** (`viewMode: 'landing'`, the default). A press-and-hold "splice" hero (hold 2 s → house lights up → "Launch Studio" appears), then an interactive exhibit (one laser-power slider driving a waveguide schematic and a branch-power equation), three capability cards, and a reference strip of OLT classes and ONT receive limits. Navigation links and a "Topologies" menu can jump straight into the studio with a preset loaded or with a mission started.

2. **Studio** (`viewMode: 'studio'`), itself four sections:
   - **Design** — a React Flow canvas with a component library on the left, a canvas, an inspector on the right, a floating toolbar, a status bar along the bottom, plus overlays (missions drawer, OTDR dialog, OPM HUD).
   - **Simulation** — read-only numbers and a subscriber table derived from the same simulation.
   - **Reports** — Bill of Materials: optical audit tab + commercial quotation/CAPEX tab, with CSV/JSON download and editable unit prices.
   - **Settings** — safety margin, auto-run, test-gear launchers, clear canvas, links.

The user places nodes (OLT, PLC splitters 1:2…1:64, fiber spans of three roles plus OM3/OM4 glass, dome closure, ODF panel, NAP/FAT, ONT, Wi-Fi 6 gateway, attenuator pad), connects their ports with patch cords, edits physical parameters in the inspector, and immediately sees a deterministic link budget: each subscriber's received power = OLT launch power − (fiber attenuation × km + splices × 0.1 dB + connectors × 0.5 dB + splitter insertion losses + ODF/NAP/attenuator/closure losses + the global safety margin). Received power is classified into OVERLOAD / ONLINE / WARNING / LOS / DISCONNECTED and drives node colours, edge colours, the status bar, and the reports. A separate CAPEX calculator multiplies deployed quantities by editable USD unit rates. Two diagnostic toys re-use the same graph: an OPM that reads simulated power at any port/patch cord, and an OTDR that synthesises a Rayleigh backscatter trace and an event table along a chosen route. Five guided missions load a preset, sometimes mutate it (laser off, a macro-bent span, an unpatched drop), and check their objectives against the live simulation on every render.

Everything is educational: copy throughout says the numbers are references, not measurements (see Part 4.5 for the exact disclaimers).

## 3.4 Connection rules

There is **no `isValidConnection` callback** — React Flow allows dragging from any source handle to any target handle. Validation happens only inside `handleConnect` (App.tsx:533-623) and `handleNodeClick`'s click-to-link path (App.tsx:764-890):

| Rule | Implementation | Applies to |
|---|---|---|
| No self-connection, no missing endpoints | `if (!source \|\| !target \|\| source === target) return` | all edges |
| A closure output must sit on a sleeved channel | `activeSpliceChannels[handleIndex]` else silently ignored | closure → anything |
| ODF outputs limited to `out-0`/`out-1` | `!['out-0','out-1'].includes(...) → return` | ODF → anything |
| NAP outputs limited to 0–7 | index range check | NAP → anything |
| Splitter outputs limited to its ratio | index `< splitterBranchPortCount(ratio)` | splitter → anything |
| Exact duplicate edge is ignored | source+target+handles all equal → unchanged | all |
| Single-input hardware is replaced | a new cord into ONT / gateway / NAP / attenuator **removes** the previous cord into that node | all |
| Closure and ODF inputs are per-port | only the cord on the same `in-n` is replaced | all |
| Single-output hardware is replaced | a new cord out of OLT / fiber / attenuator **removes** the previous cord out of that node | all |
| Branching outputs are per-port | splitter / closure / ODF / NAP replace only the cord on the same `out-n` | all |
| Subscribers cannot be link-mode sources | link mode refuses and prints the message | click-to-link |
| OLT cannot be a link-mode destination | refused | click-to-link |
| Clicking an existing source→target pair deletes it | link mode toggles | click-to-link |
| No rule prevents: subscriber into closure, splitter into ONT input, OLT into splitter input directly from the *canvas handle* drag | **absent** — any handle-to-handle drag that survives the index checks is accepted | all |

# PART 4: FEATURES AND LOGIC

## 4.1 The optical engine (`src/engine/opticalSimulator.ts`)

**Model.** `simulateTopology(nodes, edges, settings, runId)` performs a directed depth-first walk from every OLT whose `laserOn` is true, accumulating loss element by element until it reaches an ONT or gateway:

```
P_rx = P_tx − (L_fiber + L_splitter + L_ODF + L_NAP + L_attenuator + L_splices + L_connectors + L_closure + L_field_faults + Margin)
```

- `MAX_WALK_DEPTH = 96` (L62); a stack deeper than that stops silently.
- Each element contributes as follows:

| Element | Loss added | Source |
|---|---|---|
| Fiber | `lengthKm × attenuationDbPerKm` | `computeFiberLoss` L184 |
| Fiber splices | `splices × 0.1 dB` | `SPLICE_LOSS_DB` |
| Fiber connectors | `connectors × 0.5 dB` | `CONNECTOR_LOSS_DB` |
| Macro-bend fault | `+3.50 dB` when enabled | `MACRO_BEND_PENALTY_DB` |
| Dirty ferrule fault | `+2.00 dB` when enabled | `DIRTY_CONNECTOR_PENALTY_DB` |
| Splitter | catalogue loss for its ratio + `excessLossDb` | `SPLITTER_LOSS_DB` + `computeSplitterLoss` |
| ODF | `throughPortLossDb` (default 0.50) per traversal | `computeOdfLoss` |
| NAP | `splitLossDb` (default 10.50) and ×8 on the split ratio | `computeNapLoss` |
| Attenuator | pad value (1/2/3/5/10/15) | `computeAttenuatorLoss` |
| Closure | per **active branch** crossed: `spliceLossDb` (0.05–0.10, default 0.08) and +1 splice | `computeClosureSpliceLoss` |
| Safety margin | `settings.safetyMarginDb` (default 2.0), added once at the terminal | `settings` |

- **Wavelength handling**: each span's coefficient comes from `ATTENUATION_DB_PER_KM[resolveFiberWavelength(data)]`; an override wins if set and > 0. If the OLT is `XGS-PON`, every traversed span is forced to 1577 nm regardless of the span's own selector (L386-392). The terminal path records `wavelength: 1577` for XGS-PON, otherwise the OLT's own wavelength.
- **Closure gating**: a branch is only traversable when its tray channel is sleeved (`activeSpliceChannels[index]`); an unsleeved branch is skipped with no message on the canvas.
- **ODF pairing**: the walk follows only the output whose index matches the input handle index (`in-2 → out-2`), so a pair cannot be crossed by the pathfinder even though the UI allows patching any output.
- **NAP**: only `out-0…out-7` are followed; the split ratio multiplier is always 8.
- **Loops**: `onStack.has(edge.target)` prevents cycles; a topology with a loop simply stops at the repeated node.
- **Multiple OLTs**: every lit OLT is walked independently; each endpoint keeps **all** candidate paths and the highest `rxPowerDbm` wins (L560). Ties keep the first in DFS order.
- **Status**: `classifyOnt(rx)` — `> −8` OVERLOAD, `≥ −24` ONLINE, `≥ −28` WARNING, else LOS; `null` → DISCONNECTED (L231-241).
- **Margin metric**: `marginDb = rx − (−28)`, i.e. headroom **above the LOS floor**, not the remaining design margin. The UI labels it `Link margin` throughout (Part 9 flags the ambiguity).
- **`totalLossDb`** = accumulated loss **+ safety margin**, so the "Total loss" reported on the status bar includes the 2 dB margin.
- **Edge telemetry**: `recordEdge` stores `P_tx − loss` at the moment the walk crosses each cord (before the receiving element's own loss), so the pill on an edge shows the power arriving at that port. `edgeState = live` when ≥ −28 dBm, `degraded` when < −28 dBm, `idle` when unreached.
- **Upstream delta**: per OLT, the spread between the strongest and weakest connected subscriber RX; each endpoint also gets `upstreamDeltaDb = maxRx − ownRx`; a warning appears above 15 dB (`UPSTREAM_DYNAMIC_RANGE_MAX_DB`).
- **Summary** (`summarise`, L685): counts by status, total fiber km (all spans on canvas, connected or not), total splices (span splices + sleeved closure channels), total connectors (span connectors only — **connector counts on patch cords are not counted anywhere**), splitter totals by ratio, OLT active/total, mean/worst RX, upstream delta, `allOptimal`, `hasFault`, modal-dispersion warnings.
- **Determinism**: no randomness anywhere in the engine. Same graph + same settings ⇒ same numbers. `runId` and `computedAt` are the only varying fields.
- `simulatePON` is an alias kept for the tests.

## 4.4 Auto-run gate and the Run button

- `liveSimulation` is recomputed on every `nodes`/`edges`/`settings` change (memo, App.tsx:260).
- `simulation` = `autoRun ? liveSimulation : (committedSim ?? liveSimulation)` (App.tsx:268-271).
- `markDirty()` sets `dirty` on every edit path: add (L511), drop (L467), connect (L615), delete (L431/442/453), patch (L1032), clear (L1026), mission/preset apply (L710 and applyPreset path).
- ▶ `Run Simulation` sets `testing=true`, simulates immediately, stores `committedSim`, clears `dirty`, and clears `testing` after **700 ms** (L314-320). The button shows a spinner while `testing`; `title` becomes `The budget changed since the last run — run it again` while stale.
- With auto-run **off** and `dirty`, the design bar shows `UNSAVED BUDGET — RUN SIMULATION`; with auto-run **on** the chip never appears.
- There is no debounce, no worker, and no cancellation; every keystroke in a slider re-runs the full DFS synchronously.

## 4.5 Optical Power Meter (OPM)

- Entry points (the only two): the library's Tools card **`Power Meter`** (Sidebar.tsx:255-262) and the Settings screen's **`OPM Tool`** button (SettingsScreen.tsx:109-117). The canvas toolbar has **no** OPM button. Opening sets `opmActive`, which disables node dragging and selection (`elementsSelectable={!opmActive}`, `nodesDraggable=false`), swaps the cursor to `opm-probe-cursor.svg`, and suppresses clicks in a capture-phase handler so probing never selects.
- Probe resolution (`resolveProbeTarget`): element under the pointer → closest `.react-flow__handle` (port, with its `data-handleid`/type) → closest `.react-flow__edge` (patch cord) → closest node (component body). Moving off everything clears the probe.
- Reading: `readOpticalPowerAtProbe` — edge → its `powerDbm`; input port → strongest power among cords into that handle; output port → strongest among cords out of that handle, else `outputPowerAtUnpatchedPort` (computes the would-be power from upstream, so an unpatched splitter output still reads); OLT body → `laserOn ? txPowerDbm : null`; other body → strongest out, else strongest in, else unpatched estimate.
- Recalibration: selecting 1310/1490/1550 runs `simulateAtMeterWavelength`, which clones the graph with that wavelength on every OLT (and forces `ponStandard:'GPON'`) and every fiber, then re-simulates. **This never mutates the document** and never changes the committed budget.
- Display: reading to 2 dp with sign; `LO` for no light (`null`); `UNDER` for a reading below −60 dBm; ` dB` instead of ` dBm` in reference mode; backlight green only inside −28…−8 dBm, amber outside it, off for LO/UNDER.
- `REF` stores the current reading; subsequent readings show the delta with sign; pressing again returns to absolute.
- The HUD is positioned at the probe point, clamped inside the canvas, and is excluded from probe hit-testing (`.closest('.opm-meter-hud')` guard).
- No averaging, no min/max hold, no dBm/mW toggle, no auto-lambda detect, no save-to-report.

## 4.8 OTDR engine (`src/engine/otdrSimulator.ts`)

- One deterministic directed route from the selected source to the selected subscriber (`findRoute`); with no target it uses the longest reachable subscriber branch, subscriber id as tie-break.
- Sources offered: OLT and fiber nodes (`sourceLabel` = `{cableType} fiber · {x.xx} km ({id})`); targets offered: subscriber endpoints with a route.
- Wavelength: any of the seven; invalid → 1490. Pulse widths: `10`, `100`, `1000` ns; invalid → 100.
- Events are synthesized per element: `launch`, `fiber_span`, `connector`, `splice`, `splitter`, `odf`, `nap`, `attenuator`, `fault_bend`, `end_of_fiber`. Splice/connector/fault positions are **distributed evenly along each span** because the canvas stores only span totals (the UI says so explicitly).
- Pass/fail rules: splice ≤ 0.3 PASS, ≤ 0.8 WARNING, else FAIL; splitter excess ≤ 1 PASS, ≤ 3 WARNING, else FAIL; ODF/NAP/attenuator/connector PASS; injected fault FAIL.
- The trace is 0–35 km, `+5` to `−45` dB, with a noise floor; hover shows a crosshair readout; acquisition shows a scanline for ~900 ms before the trace appears.
- The OTDR result is **not** fed back into the link budget and **not** exported.

## 4.11 Validation and error handling

- No form validation blocks input: numeric fields coerce with `Number(...) || 0`, so typing `abc` becomes 0; negative values clamp to 0 in most fields, but `PON port name`, `Subscriber`, `Serial`, `SSID` accept any string including empty.
- Deleting a node silently deletes its cords (React Flow default) with no confirmation; only the inspector's `Remove component` has a two-step confirm.
- `Clear canvas` has **no** confirmation and is a single click in Settings (App.tsx:1420).
- The library search's only empty state is the sentence quoted in 2.5; there is no "no results" for the accordion because filtering hides whole categories.
- Network, fetch, or async errors cannot occur (no data fetching). The only async surfaces are the three lazy chunks and the two simulated timers; a chunk load failure would throw into `ErrorBoundary`.
- No `alert()`, `confirm()`, or `prompt()` exists in the codebase — all confirmations are inline components.

# PART 5: DESIGN SYSTEM

The product loads **four** stylesheets in this fixed order (`main.tsx`): `tokens.css` → `global.css` → `theme.css` → `photo-ui.css`, then React Flow's own `@xyflow/react/dist/style.css`. Each later file is allowed to override the previous one, and all three component stylesheets contain broad element/`!important` rules, so the cascade is load-order dependent.

## 5.1 Token layer (`src/styles/tokens.css`, 7.5 KB)

**Type scale — 7 steps, locked in a comment:** `--fs-2xs 11` (micro: uppercase chip, unit suffix, node art) · `--fs-xs 12` (label) · `--fs-sm 13` (body, "never smaller") · `--fs-md 15` (lead) · `--fs-lg 18` (panel title) · `--fs-xl 22` (section/modal title) · `--fs-2xl 28` (display heading, large metric).

**Semantic roles:** `--type-display clamp(45px,5.25vw,76px)` · `--type-display-sm clamp(33px,3.7vw,52px)` · `--type-section-title 22` · `--type-section-title-lg 28` · `--type-panel-title 18` · `--type-card-title 15` · `--type-subtitle 15` · `--type-body 13` · `--type-small 12` · `--type-caption 11` · `--type-metric 28` · `--type-metric-sm 22` · `--type-brand 22`.

**Weights:** 400 / 500 / 600 / 700 / 800 (the 800 is documented as "wordmark only").
**Leading:** 1 / 1.2 / 1.35 / 1.5 / 1.6.
**Tracking:** display −0.07em, tight −0.02em, label 0.08em, eyebrow 0.13em.
**Spacing:** 4 / 8 / 12 / 16 / 24 / 32 (`--sp-1…--sp-8`), with a comment forbidding 5/6/7/9/10/11/13 px in component CSS.
**Radius:** 6 / 8 / 10 / 12 / 16 / 999.
**Layout tokens:** `--topbar-h 56` · `--rail-w 84` · `--library-w clamp(200px,17vw,240px)` · `--inspector-w clamp(340px,26vw,420px)` · `--inspector-w-collapsed 44` · `--shell-gap 16` · `--shell-pad 16` · `--canvas-min-w 360` · `--panel-head-h 48` · `--tabbar-h 52` · `--tab-h 40` · `--card-pad 12` · `--toolbar-gutter 208` · `--page-max 1390` · `--page-gutter clamp(16px,4vw,72px)`.
**Controls:** `--control-sm 32` · `--control-md 36` · `--control-lg 40` · `--control-tap 44`.

**Token overrides by breakpoint:** ≤900 px `--type-display clamp(48px,7vw,68px)`; ≤640 px `--type-display clamp(41px,11.5vw,60px)`, `--type-display-sm clamp(30px,9vw,42px)`, `--type-section-title-lg → 22`; ≤1280 px topbar 52, library 208, inspector 360; ≤1024 px library 184, inspector 344, `--canvas-min-w 320`, shell gap 8, shell pad 12; plus the ≤900 and ≤560 blocks listed in Part 6.

## 5.3 Typography in practice

- **Manrope** is the UI face everywhere (`--fiber-*` shell, body copy, buttons, landing). **JetBrains Mono** is used for every number, id, port name, dBm reading, table figure and code-like label (`.font-mono` + `--pu` readouts). **Sora** appears only for the phone logo mark (`photo-ui.css:2857`).
- Landing display: `--type-display` clamp (45–76 px desktop, 48–68 at ≤900, 41–60 at ≤640) with `--tracking-tight`; eyebrows are 11–12 px uppercase with 0.13em tracking.
- Studio titles: `pu-screen h1` 22–28 px bold; panel titles 18 px; design-bar title 15 px; body 13 px; captions 11 px. Inspector form labels are 11 px uppercase (`field-label`), values 12–13 px mono.
- One deliberate deviation from the token system: a single `text-[26px]` literal exists in TSX (the only arbitrary `text-[Npx]` in `src/`).
- Numeric alignment: every metric is right-aligned mono inside tables; the status bar and inspector metrics are left-aligned mono. `font-variant-numeric: tabular-nums` is declared on five rules only (`global.css:175`, `photo-ui.css:800,928,1965,2039`), so readouts outside those rules depend on JetBrains Mono's own digit widths (which are tabular by design) and on the fallback chain when the webfont fails.

## 5.4 Spacing, radius and elevation

- Panel gutter is a single 16 px value (`--panel-pad`), narrowed to 12 px at ≤1024. Cards use 12 px padding, 8–12 px radius; modals 16 px radius; pills 999 px.
- Borders are 1 px `--pu-line`; the canvas card is white with a 1 px hairline, 12 px radius and an inset shadow.
- Two shadow languages: Tailwind `shadow-panel` (`0 1px 2px rgba(43,26,20,.05), 0 12px 28px -20px rgba(43,26,20,.24)`) and a set of hand-written `box-shadow` values in the CSS files (node cards, sheets, FAB, meter). Hover states mostly raise the shadow slightly and shift 1 px up.
- Focus is drawn with a 2 px `--pu-pri` ring plus 2 px offset on interactive elements in the React components; a grouped rule covers `.pu-tool`, `.pu-rail button`, `.pu-menu button` and `.pu-doc-tab` (`photo-ui.css:1544-1547`), but the library category headers (`.pu-acc-head`), the pricing inputs and several node-level buttons have no `:focus-visible` styling and fall back to the UA outline.

## 5.5 Motion

- Shared easing `--fiber-ease cubic-bezier(0.2,0.75,0.25,1)`; React Flow transitions use 120–220 ms; sheets/screens 300–380 ms; the studio/landing cross-fade is 380 ms.
- Named animations: `optical-flow` (**defined twice**, `global.css:237` and `theme.css:210`), `simulation-pulse-glow`, `splice-ray`, `splice-action-in`, `lab-pulse`, `waveguide-ray-flow`, `otdr-scanline-sweep`, `otdr-radio-pulse`, `otdr-modal-in`, `otdr-backdrop-in`, `mission-drawer-in`, `mission-check-in`, `pu-sheet-in`, `pu-overlay-spin`.
- Four `@media (prefers-reduced-motion: reduce)` blocks switch most of these off (edge dashes, hero ray, scanline, sheet slide, spin). The hero hold-to-splice progress bar still animates under reduced motion because it is driven by JS `requestAnimationFrame`, not CSS.
- Durations are hand-picked per component (150/160/180/220/380/500/650/700/900 ms); there is no motion token.

## 5.6 Iconography

`lucide-react` only, one weight (default 2 px stroke), sizes 12 / 13 / 14 / 16 / 18 / 20 / 24 depending on surface; every icon inside a control is `aria-hidden="true"` **except** in the rail/tab bar, where the icon is the visual anchor and the accessible name comes from `aria-label`. No pictorial emoji exist as icons, but two strings contain emoji glyphs as text: `⚠️ MODAL DISPERSION LIMIT: …` (`types.ts:185-186`) and the `⚠` prefix in the OLT node warning. The other glyph-like characters are `●`, `→`, `·`, `×`, `λ`, `Δ`, `Σ`, `θc`, `−`, `μm` and the check mark drawn as an SVG.

## 5.8 Design-system consistency observations (facts only)

1. Three parallel palettes and two naming systems coexist; the warm `--pu-*` set, the `--fiber-*` primitives and the Tailwind `noc`/`slate` sets describe overlapping roles with different hex values.
2. `noc-950` is the *lightest* value in the scale while `noc-100` is the *darkest* — the naming is inverted relative to Tailwind convention, and several components therefore read as "dark card on light page" only by accident of the chosen index.
3. `optical-flow` is defined in two files with different keyframe bodies; which one wins depends on load order.
4. The token file forbids sub-13 px body text, yet `--type-caption` (11 px) is used for running sentences in `.otdr-model-note` (`theme.css:3247-3252`, with a 1.55 line-height), the mission-drawer footer and the OPM state line.
5. No shared `EmptyState`, `Badge`, `Button` or `Dialog` component exists; each surface re-implements the pattern in Tailwind classes or bespoke CSS.
6. Icon stroke width is never set, so `lucide-react`'s default 2 px is used at 12 px (heavy) and 24 px (thin) alike.

## 6.10 Responsive problems visible in the code (no fixes proposed)

1. **Two competing ≤900 rules for `.pu-toolbar`** — the earlier one sets `max-width: calc(100% − 16px)`, the later one sets `flex-wrap: nowrap; overflow-x: auto`. The later wins, so between 768–900 px the toolbar scrolls horizontally, and its `⋯` popover is forced to `position: fixed` to escape the clip.
2. **Toolbar width vs. item count at ≤767** — 8 × 44 px cannot fit a 360 px screen; the documented "fits one row" assumption is off by one control.
3. **`.pu-top` scrolls horizontally ≤900** with no visible affordance (scrollbar suppressed), so the right-most control (Run Simulation) can be off-screen on first paint.
4. **Canvas floor of 320 px at 1024** leaves the drawing area narrower than the two side panels combined (528 px).
5. **Overlay sheets can overlap each other at 768** (library 184 + inspector 344 + rail 84 = 612 px of 768 px).
6. **Status bar, library sheet, inspector sheet and tab bar all compete for the bottom 40 % of a phone screen**; opening the inspector closes the status sheet (one-sheet policy) but opening the library does not close the inspector.
7. **`100vh` fallback before `100dvh`** in `.pu-shell` — correct for modern browsers, but the sheet caps switch from `vh` to `dvh` only inside `@supports (height: 1dvh)`.
8. **The OTDR dialog** switches to a stacked layout at ≤640 but keeps a 720 px-wide event table inside a scroll container; the cursor readout, legend and 7-column table are all still present at 360 px.
9. **`.pu-tool .th` changes shape at ≤1024** (`photo-ui.css:1501-1506`: 44 × 36 instead of the square thumbnail) while `.pu-comp` narrows to 184 px, so the thumbnail stays wide but loses height exactly where the panel is also narrower.
10. **No container queries** are used anywhere; every adaptation is viewport-based, so the library inside its 184 px column makes the same layout decisions as a 1200 px canvas.

# PART 7: USER JOURNEY

Every step below names the exact text the user sees. Line refs are to the component that owns the step.

## 7.1 First visit (cold load, desktop)

1. `index.html` paints its static shell; the bundle mounts. `viewMode` starts as `'landing'` (App.tsx:1454) so the **overview page** is the first screen. The studio is already mounted behind it with `inert` + `aria-hidden` (App.tsx:1462-1465,1507), and its canvas is **empty** (`initialTopology()` returns `[]`, App.tsx:206-208).
2. Above the fold: nav (`FiberLAB` wordmark, `Capabilities`, `Reference`, `Topologies`, `Launch Studio`), hero eyebrow `FIBER ACCESS NETWORK LAB`, `<h1>` `Splice the fiber. / Light the home.`, lede `Build a fiber-to-the-home network and simulate its optical performance.`, and the **hold-to-splice** button `HOLD TO SPLICE`.
3. Below: the interactive exhibit (`Drag the laser. Watch the light fade.` with the 1–7 dBm slider, the wave-guide drawing, `P_branch = P_tx − 7.20 dB`, the live branch power), the three capability cards, the reference plate, the footer sentence.

## 7.2 The splice ritual

- Press and hold the button (`aria-label="Press and hold to splice the fiber"`, `title="Hold for two seconds to splice the fiber"`). Label goes `HOLD TO SPLICE` → `KEEP HOLDING` → `SPLICING {n}%`; the progress ring fills over 2 000 ms; a screen reader hears `Splicing started. Keep holding for two seconds.`
- Releasing early resets and announces `Splice released early. Press and hold again to splice the fiber.`
- Completing it: the scene lights up, the button becomes the inert chip `SPLICE COMPLETE`, a primary `Launch Studio` appears, the phone vibrates 18 ms, and the live region says `Splice complete. The light crosses the fiber and the home is lit. Launch Studio is ready.`
- Skipping the ritual is possible: `Launch Studio` in the nav works immediately, and so do the `Topologies` presets and the hero's `Load Standard 1:32 GPON Tree` / `Load Failing Link` buttons.

## 7.3 Exploring the overview page

- Drag the laser: readout counts to the new value, the ray brightens, four `PIGTAIL` cards update, and the equation recomputes `−2.20 dBm`-style values live. Notes under the slider read `+1.0 dBm`, `Class C+ · +3 to +7 dBm` (or `Below Class C+ range`), `+7.0 dBm`.
- Open `Model scope & assumptions` for the long caveat paragraph; open a card's `Topologies` menu to load a preset **from the landing page**, which switches straight to the studio with that topology.
- `Launch Mission 1 · The Marginal Villa` in card 02 enters the studio, loads the mission topology and opens the drawer.
- `Open the plant audit in Studio` in card 03 enters the studio on the Design screen (it does **not** open Reports despite the label).
- `Reference` jumps to the class table; `Capabilities` jumps to the cards.

## 7.4 Entering the studio

- `Launch Studio` (nav or post-splice) → cross-fade 380 ms to the studio; focus moves to `#studio-overview-toggle` (the wordmark, which is also the "back to overview" control). The canvas is empty and shows `The canvas is empty` / `Drag in an OLT, or let a mission walk you through it.` plus `Open the mission` and a dismiss `×`.
- The design bar shows the preset select (`FTTH Network`), the first-run card (`1 Pick a component` · `2 Connect them` · `3 Press Run Simulation`) and no status chip.
- Until a first mission/preset is loaded, `activePresetId` is `null`, so the top bar reads `FTTH Network Design` and `dirty` is false — even though the canvas is empty. Pressing `Run Simulation` on an empty canvas simulates nothing, clears `dirty`, and the status bar reads `No subscribers`.

## 7.5 Building a network

1. Open the library (or press `+ Components` if collapsed). Search `splitter`, or expand `Splitters` → `1:8`.
2. Click a card → `handleQuickAdd` drops it at the visible canvas centre with a cascade offset; the library folds on narrow screens. Drag a card → drops where released (`screenToFlowPosition`).
3. Wire it: drag handle → handle (the cursor turns into a crosshair; each node's handles have `SC/APC …` labels), or use `Connect` on the toolbar and click source then target, watching the bottom panel say `Source: splitter-… Now choose a destination node.` then `Connected splitter-… to fiber-….`
4. Every edit sets `dirty`; with auto-run on the numbers update instantly, with it off the design bar warns `UNSAVED BUDGET — RUN SIMULATION`.
5. Select any node → inspector opens (340–420 px or a sheet), identity card + beginner sentence + `Properties` / `Optical Power` / `Info`. `Advanced` reveals sliders and tables. Editing a field is immediate — there is no Apply button and no undo.

## 7.6 Running and reading the result

- `Run Simulation` (top bar or Simulation screen) runs the DFS, shows a spinner for 700 ms, and commits the result.
- Status bar: `OK` / `Marginal` / `Fail` + `Total loss`, `Total distance`, `Subscribers OK`. Expand → `Optical Budget` bars (`OLT Launch`, `After Splitter`, `Closest ONT`, `Farthest ONT`) or `Events` list; clicking an event row selects and fits that node.
- Rail → `Simulation`: stat cards, the same bars, and a per-subscriber table with `Design →` per row.
- Rail → `Reports`: `Bill of Materials`, CAPEX chip, `Quote CSV`, `Quote JSON`, the audit tab, the commercial tab with editable unit rates.

## 7.7 Following a mission

1. `ListTodo` in the toolbar (or `Open the mission`, or Settings → `Missions`) opens `Field missions`. The drawer is `Missions by skill` with three sections and five missions; the first is preselected.
2. Read `Scenario brief` → press `Start mission`. The topology is replaced by the mission's preset, the safety margin is forced to the mission value, the mission becomes `Active`, and objectives begin ticking in real time.
3. `Restart mission` reloads the scenario; `Field hints` opens the numbered hints; completing every objective reveals `Mission complete` with `Mean Rx` / `Worst Rx` / `Margin` and the endpoint count.
4. Nothing records that a mission was ever completed; opening another mission abandons the first without a warning.

## 7.8 Using the instruments

- **OPM:** Settings → `OPM Tool` (or Tools → `Power Meter`). The cursor becomes a probe; hover a port, cord or node and the HUD appears with `FIXED`-style readout, `SIMULATED PATH @ 1490 nm`, wavelength buttons `1310/1490/1550`, `REF` and `Close OPM`. Clicking in probe mode never selects or drags. `Escape` leaves probe mode.
- **OTDR:** Settings → `OTDR Trace`. Choose `Launch source` and `Target branch`, a `Wavelength` and a `Pulse width`, press `ACQUIRE TRACE / PULSE LASER`, watch `PULSING FIBER…` for ~900 ms, then read the trace (`CROSSHAIR READOUT · HOVER TRACE` → live cursor values) and the `Automated event table` with `PASS` / `WARNING` / `FAIL` chips.

## 7.9 Returning, refreshing, and losing work

- The wordmark (`Overview & Physics`) returns to the landing page **without** discarding the studio: the React tree is kept mounted behind an `inert` layer, so the in-memory design survives a round trip within the session.
- A **page reload discards everything except the onboarding dismissal**: no `localStorage` key, no IndexedDB, no URL state. The studio returns empty.
- The crash screen promises `Your design is kept in this browser session, so reloading the workbench is safe.` — for any reload after a crash the design is in fact gone.
- `Clear canvas` (Settings → Workspace, `aria-label="Clear Canvas"`) empties the graph instantly, with no confirmation and no undo; the only trace is that the preset name drops back to `FTTH Network Design`.

## 7.10 The phone journey (code-derived)

1. Landing: hero art and headline at ≈41 px; nav wraps; the compact wave guide replaces the wide one; the hold button is full-width; the exhibit stacks.
2. `Launch Studio` → studio with **no rail**: the four sections live in the bottom tab bar; the top bar scrolls sideways; the canvas takes the full width (≈336 px at 360).
3. Library = bottom sheet with a drag handle; inspector = bottom sheet; status = floating pill → sheet. Only one of inspector/status is open at a time; the library can be open at the same time as either.
4. Toolbar sits as a 44 px icon strip above the status pill; the `⋯` menu opens upward; zoom is pinch-only (the top-bar zoom select and React Flow controls are both hidden).
5. Every destructive action is either a long-press-free single tap (`Delete` in the toolbar) or two-step (inspector footer). Tapping a node never zooms (by design after the earlier fix), so the only way to inspect a small node is pinch-zoom.
6. Nothing in the phone layout offers a way to reach `Run Simulation` if it is scrolled out of the top bar other than scrolling that bar.

## 7.11 Accessibility journey

- Tab order follows DOM order; the landing page's first stop is `Overview` (the brand link), then nav items, then the hold button. The studio's first stop is the wordmark.
- Section changes move focus to the new `<h1>` (`useSectionFocus`), and the three lazy dialogs trap focus and restore it on close.
- The rail and tab bar are `nav` landmarks with `aria-label`s; the status bar is a labelled section; the OPM HUD is a `region` with a live reading; toasts do not exist — instead the status panel and inline messages announce.
- Colour is not the only signal: statuses carry text labels (`ONLINE`, `WARNING`, `LOS`, `DISCONNECTED`, `OVERLOAD`) plus a dot; edges carry a pill with a power value or `idle`. The word `MARGINAL` appears only inside the landing card's illustration, not as a live status label.
- Known gaps: no skip link; the canvas nodes are `div`s with `aria-label`s on handles but no keyboard pathway to select or move them; the OTDR chart is a single `role="img"` with a long `aria-label` (no table alternative for the trace itself, although the event table follows); and the `title`-only tooltips (toolbar, handles) are not reachable by keyboard.

# PART 9: OBSERVATIONS

Factual findings, ordered by impact. No fixes are proposed. Severity is my judgement of user consequence: **S1** blocks normal use or loses work, **S2** misleads or contradicts, **S3** friction, **S4** polish.

### S1 — The tool cannot keep a design

1. **Nothing is persisted.** `nodes`, `edges`, `settings`, `unitCosts`, `activePresetId`, `activeMissionId` are all React state (`App.tsx:217-240`); the only storage write in the whole app is `localStorage.setItem('fiberlab.onboarding.dismissed', '1')` (`DesignBar.tsx:16,30`). A reload, a crash, a back-navigation out of the SPA, or closing the tab destroys the network. For a workbench whose output is a designed network and a quotation, the primary artefact is the most volatile object in the app.
2. **The crash screen makes a false promise.** `Your design is kept in this browser session, so reloading the workbench is safe.` (`ErrorBoundary.tsx:73-74`) — the `Reload Workbench` button is the one action that guarantees the design is gone.
3. **`Clear canvas` is irreversible and unconfirmed.** One click in Settings → Workspace (`SettingsScreen.tsx:152-160`, `App.tsx:1420-1423`) wipes nodes, edges, mission, preset and selection. There is no undo stack anywhere in the codebase, so this cannot be recovered.

### S2 — Numbers and labels that say something other than what they mean

4. **`Link margin` is headroom above LOS, not design margin.** `marginDb = rxPowerDbm − (−28)` (`opticalSimulator.ts:558`). A reading of −28 dBm therefore shows `Link margin 0.00 dB` and a reading of −24 shows `4.00 dB`, while the actual budget margin (after the 2 dB allowance) is a different quantity that is never displayed as such. The label appears in the inspector (ONT and gateway), in the Simulation table and in the mission-complete tiles.
5. **`Total loss` includes the safety margin.** `totalLossDb = state.lossDb + safetyMarginDb` (`opticalSimulator.ts:349`), so the status bar's `Total loss`, the inspector's `Total path loss` and the BOM's `Loss dB` all include 2 dB that is not a loss. Raising the margin in Settings raises "total loss" with no wording change.
6. **The XGS-PON walk overrides span wavelengths silently.** The simulator forces every span to 1577 nm on an XGS-PON route (`opticalSimulator.ts:386-392`), but the fiber node art computes its pill from the node's own `data.wavelength` (`FiberNode.tsx:16,26`). A span set to 1310 nm on an XGS-PON route therefore shows `0.35 dB/km` on the canvas while the budget used `0.22 dB/km`; the two disagree by design.
7. **1:32 and 1:64 splitters expose only 16 ports but multiply the split ratio by 32/64.** `splitterBranchPortCount = min(ratio, 16)` (`types.ts:100-102`) caps the handles, while `cumulativeSplitRatio *= node.data.ratio` (`opticalSimulator.ts:494`) uses the full ratio. The inspector explains this in prose (`A 1:32 cassette terminates 16 branch ports here…`), but the canvas shape is identical for 1:16, 1:32 and 1:64, and the artwork for all three draws four output ferrules (`SPLITTER_ART` entries 16/32/64 are the same drawing).
8. **The status vocabulary is split.** The status bar says `OK` / `Marginal` / `Fail` / `No subscribers` (`StatusBar.tsx:41-55`); badges everywhere else say `ONLINE` / `WARNING` / `LOS` / `DISCONNECTED` / `OVERLOAD` (`types.ts:348-382`); the Reports sub-line says `optimal · marginal · overload`; the landing illustration says `MARGINAL`. Four names for two states.
9. **`Fibre profile` vs `fiber`.** The inspector field is labelled `Fibre profile` (`Inspector.tsx:816`) while the rest of the product is consistently `fiber` (library `Fiber Cables`, BOM `Fiber spans`, prose "fiber"). Same document, two spellings.
10. **The landing CTA misdescribes its destination.** `Open the plant audit in Studio` (`PillarsGrid.tsx`) calls `onOpenStudio`, which opens the **Design** canvas, not the audit. Likewise `Launch Mission 1 · The Marginal Villa` hard-codes "1" although the mission list opens on `Rescue the Unpatched Subscriber`.
11. **Two browser menus still offer Fit.** The canvas toolbar's Fit was removed as requested (verified: no Fit in `CanvasToolbar.tsx`), but `Fit to screen` remains in the top-bar zoom menu (`TopBar.tsx:104`) — the affordance is gone from one place and kept in another.
12. **Advertised keyboard shortcuts do not exist.** The toolbar tooltips promise `Select and move components (V)` and `Pan the canvas (H)`; no keydown handler maps `V` or `H` anywhere (`grep` finds none). The only working shortcuts are `Delete`/`Backspace`, `Escape`, `Space`/`Enter` on the splice button, and Tab within dialogs.

### S2 — Content that over-claims

13. **Status detail texts are committed to specific failure physics without qualification.** `Receiver saturation — optical burn risk. Add attenuation.` claims a burn risk the model does not compute; `Marginal link — high BER risk` asserts a BER consequence the model does not simulate. The rest of the product is scrupulous about marking its simplifications, which makes these two sentences stand out.
14. **`Total distance` counts every span on the canvas**, connected or not (`summarise` adds `lengthKm` for every fiber node), while `Total loss` only follows reachable paths. A disconnected 10 km span raises distance and not loss, and nothing on screen says so.
15. **`Estimated down / up` is line rate ÷ cumulative split ratio** (`estimatedDownMbps`), explicitly labelled as an estimate with a caveat — but it is the only Mbps figure in the UI and reads as a service speed in a per-subscriber table.
16. **27 separate occurrences** in `src/` say some variant of "not a measured value / learning model / illustrative / educational" (grep count over `not a measured|not a calibrated|learning model|educational|illustrative|not a specific`), and the word "learning" alone appears 13 times. The caveat density is high enough that a first-time reader meets three disclaimers before meeting the first number.

### S3 — Interaction gaps

17. **Objective progress is only evaluated while the missions drawer is open.** `evaluateMissionObjectives` is called in `MissionDrawer.tsx:55`; the app itself never computes it. A user who closes the drawer to go and fix the network gets no ticking, no toast, and no completion signal — the `Mission complete` banner lives entirely inside the closed panel.
18. **An active mission is invisible on the canvas** except for the toolbar's `is-active` tint and the `Missions, active: …` aria/label on the Settings button. There is no banner, no objective chip, no highlighted mission target node.
19. **`Linked` state is invisible.** The auto-chosen port is never shown; `Connected splitter-… to fiber-….` is the only feedback, and it disappears when the next interaction replaces the message.
20. **Recent components are not re-addable as nodes.** Chips remember the library item (with its payload), not any placed component; they cannot reselect or reveal a node already on the canvas (`Sidebar.tsx` recents store `ToolboxItem`).
21. **Library category state is a single open accordion**, so comparing splitters to closures means collapsing one to open the other; search results bypass the accordion entirely and show category labels instead.
22. **`Delete` on the keyboard deletes instantly, but the inspector's own delete is two-step.** The same action has two different safety levels depending on where the user is looking.
23. **Empty-state dismissal is session-only** and returns on reload, while the "Recent" list — which is also session-only — silently resets each time the page reloads. Two different lifetimes for two chrome elements that look equally permanent.
24. **The top bar can hide `Run Simulation`.** ≤900 px the bar scrolls horizontally with the scrollbar suppressed; on a phone the primary action can start off-screen and nothing indicates the row scrolls.
25. **Numeric fields silently coerce garbage to 0** (`Number(event.target.value) || 0`), so a mistyped attenuation or span length becomes a legitimate-looking zero rather than an error.
26. **The OPM reference resets when the HUD remounts** (`referenceDbm`/`relativeMode` live in `OpmMeterHud.tsx:24-25`); closing the probe or switching tools drops the stored 0 dB reference without telling the user.

### S3 — Engineering and maintenance signals

27. **The CSS cascade is load-order-dependent and duplicated.** Three stylesheets style the same components; `.pu-toolbar` has two competing `@media (max-width: 900px)` blocks (`photo-ui.css:1559-1613` and `2397-2448`); `@keyframes optical-flow` is defined twice (`global.css:237`, `theme.css:210`); `!important` appears throughout `photo-ui.css`.
28. **Four palettes, seven greens.** `--fiber-*`, `--pu-*`, the Tailwind `noc`/`slate` overrides and 357 raw hex literals in CSS coexist (236 + 88 + 33). `noc-950` is near-white and `noc-100` near-black, inverting the usual scale direction.
29. **The design system's own rules are not enforced.** The token file states that body copy never goes below 13 px and that raw px values should not be used; `--type-caption` (11 px) is applied to multi-sentence notes, and one `text-[26px]` literal exists in TSX.
30. **Fonts come from Google Fonts** (`index.html:41-46`) with `preconnect` but no self-hosting and no CSP meta tag anywhere; the app therefore needs two third-party hosts to render as designed, and an offline or locked-down deployment falls back to system fonts.
31. **No routing.** The product has two states (`landing`/`studio`) and four sections held in React state plus `history.pushState` for section changes only (`useSectionHistory`). Nothing is deep-linkable; a shared URL always lands on the overview page with an empty canvas.
32. **The export format has no importer and no version handling.** `TopologyExport` v2 is written by `buildQuotationExport` and nothing in `src/` reads it; `format`/`version` are constants. The JSON also omits `bestPaths` and `edgeTelemetry`, so per-edge power cannot be reconstructed from the file.
33. **Metadata drift.** `<title>FiberLAB . Kara Nawzad</title>` uses a spaced full stop where the rest of the brand uses `·`; `index.html` declares `https://karanawzad.tech/FiberLab/` as canonical while `package.json` says `https://kara-nawzad.github.io/FiberLAB/`; OG/Twitter images point at the custom domain.
34. **Dead or test-only surface.** `simulatePON` exists only as an alias for the test suite (`opticalSimulator.ts:683`); `WAVELENGTH_REFERENCES[1550]` hard-codes `0.2` instead of reading the table; the 1550 nm "diagnostic reference" is offered in the fiber selector although the budget is a downstream PON model.
35. **Verification depth.** 138 Vitest tests pass, but they are unit/integration tests in jsdom; there is no end-to-end test, no visual-regression test, and no accessibility test. Several tests assert exact marketing copy (e.g. `/System safety margin/`, `/Hold for two seconds/`), so copy edits break the suite.
36. **Documentation outweighs the app.** `docs/PROJECT_GUIDE.md` is 102 982 bytes and the design mock `docs/design/hardware-ui-mock.html` is 74 883 bytes, against a `src/` tree of 952 952 bytes including tests; the mock is shipped in the repo but not in the build.
37. **Responsive verification is impossible in this environment.** The 38 media blocks and the phone sheet system are coherent in code, but nothing in this audit confirms them visually; the toolbar row arithmetic (8 × 44 px vs ≈320 px) is the clearest place where the code's own comment and its own numbers disagree.
